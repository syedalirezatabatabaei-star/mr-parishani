# بازیابی پشتیبان

**مرجع:** `docs/decisions/task-10-2-plan.md` (WAL-G، PITR، Redis، S3) و چک‌لیست سند ۱۹ §۱۰-۲.

**هدف‌ها (تصمیم ۱۰.۲):**
- RTO ۴ ساعت: از کشف تا باز شدن برنامه.
- RPO ۱۵ دقیقه: بیشترین داده‌ای که از دست می‌رود.

## پیش از شروع

1. **حادثه ثبت شود** (`incident.md`)، شدت ۱.
2. **زمان هدف بازیابی (UTC) تعیین شود:** آخرین لحظه سالم. برای خرابی سخت‌افزار «آخرین WAL»؛ برای خطای انسانی (مثلاً حذف اشتباه) لحظه پیش از آن.
3. **برنامه و worker متوقف شوند**، تا چیزی روی پایگاه خراب نوشته نشود. پایگاه خراب **حذف نشود**؛ برای بررسی کنار بماند.
4. **دو نفر حاضر باشند:** کلید رمزگشایی پشتیبان نزد دو نفر است (R8).

## بازیابی Postgres

1. **سرور تازه** Postgres 17 با پارامترهای ۱۰-۲ §۱.
2. **دریافت پشتیبان پایه:** `wal-g backup-fetch "$PGDATA" LATEST`، یا نام پایه پیش از زمان هدف (`wal-g backup-list`).
3. **فایل `recovery.signal`** و در `postgresql.conf`:
   ```
   restore_command = 'wal-g wal-fetch %f %p'
   recovery_target_time = '<UTC>'
   recovery_target_action = 'promote'
   ```
4. **آغاز Postgres؛** پایان بازیابی را در لاگ ببین (`database system is ready to accept connections`).
5. **چک‌لیست سند ۱۹ §۱۰-۲:**
   - نقش‌ها (`sepehr_owner`، `sepehr_app`، `sepehr_report`)؛
   - grantهای سطح پایگاه؛
   - schema `public`؛
   - شمار `drizzle.__drizzle_migrations` برابر آخرین شمار ثبت‌شده؛
   - `pnpm --filter @sepehr/api exec drizzle-kit generate` بی تغییر.
6. **`pnpm ops:launch-check`:** بند ۱ (نقش برنامه) و مهاجرت‌ها PASS.

## راه دوم: dump منطقی (اگر WAL-G در دسترس نیست)

```sh
age -d -i <key.txt> sepehr-<time>.dump.age | pg_restore -d "<admin url>" --no-owner --role=sepehr_owner
```

سپس همان چک‌لیست. **داده پس از زمان dump از دست رفته است.** RPO این راه تا ۲۴ ساعت است، پس فقط اگر WAL-G شکست بخورد.

## پیش از باز کردن برنامه

1. **تطبیق‌ها دستی، با worker یک‌باره** (یا با فراخوانی کارهای زمان‌بندی‌شده): دفتر کل، پیش‌پرداخت و تسویه. **هر سه باید پاک باشند.** اگر نیست: `ledger-mismatch.md`، و برنامه بسته می‌ماند.
2. **Redis:**
   - اگر Redis هم از دست رفته، کارهای منتشرشده و مصرف‌نشده باید دوباره در صف بروند (۱۰-۲ §۴).
   - ابزار (۱۴۰۵/۰۷/۲۴): اول `pnpm ops:outbox-requeue --since <زمان snapshot Redis، ISO> --dry-run`، سپس همان بی `--dry-run`. فقط شمار چاپ می‌کند: بررسی‌شده، انجام‌شده، هنوز در صف، دوباره در صف.
   - Postgres را فقط می‌خواند. `--since` حداکثر ۳۰ روز پیش است، تا ادعاهای `processed_events` هنوز بایگانی نشده باشند.
   - **پیش از باز کردن worker** اجرا شود؛ اجرای دوباره بی‌خطر است (کار موجود دوباره افزوده نمی‌شود).
3. **ترتیب باز کردن:** API، سپس web و admin، و **worker آخر**.
4. **ثبت:** RTO و RPO واقعی در گزارش حادثه.

## فایل‌های S3

- **حذف یا بازنویسی تصادفی:** از نسخه قبلی خود سطل (نسخه‌بندی روشن است).
- **از دست رفتن سطل:** از نسخه دوم شبانه روی ارائه‌دهنده دیگر.
