# صفحه نقش‌ها و دسترسی‌ها (م۱۰) — تصمیم‌ها

دستور مالک ۱۴۰۵/۰۷/۲۴ (بند ۵): «هر کار غیرمالی و بدون ورودی مالک که مانده انجام بده (صفحه‌های پنل مشاور/نقش‌ها …)». غیرمالی؛ بی مهاجرت.

## ساخته شد

- **پنل داخلی، `/access`، «نقش‌ها و دسترسی‌ها»:**
  - جدول نقش‌ها با مجوزهایشان (`access.read_roles`).
  - نقش تازه و ویرایش مجوزهای نقش غیرسیستمی (`access.manage_roles`). نقش سیستمی فقط با مهاجرت، همان قاعده سرویس (`system_role_locked`).
  - یافتن حساب کارمند یا مرکز با نام کاربری؛ نقش‌های فعلی، دادن نقش با دامنه و دلیل، لغو با دلیل (`access.assign_roles`).
  - درخواست خروج کارمند، و فهرست در انتظار با «تأیید خروج» و «رد» برای نفر دوم (مجوزهای 0087).
- **API تازه (فقط خواندنی):** `GET /access/accounts/by-username/:username`، با `access.assign_roles` یا `identity.request_staff_offboarding`.
  - فقط کارمند یا مرکز؛ بیمار هرگز (نقش برای بیمار نیست، سند ۰۴ §۶). موبایل برنمی‌گرداند.
  - از درگاه `ACCOUNT_DIRECTORY` (`findStaffByUsername`)؛ ماژول access جدول identity را نمی‌خواند.
- **`targetUsername`** در نمای درخواست خروج (افزودنی)، تا نفر دوم ببیند درباره چه کسی تصمیم می‌گیرد.
- **`@ZodResponse`** روی `GET /access/roles`، `POST /access/roles`، `GET /access/accounts/:id/assignments` و `POST /access/assignments`؛ رفتار بی‌تغییر، فقط نوع پاسخ در کلاینت.

## تصمیم‌ها

1. **نام مجوزها به همان کد** (مثل `access.read_roles`)، گروه‌بندی‌شده با ماژول. برچسب فارسی برای ۱۰۰+ مجوز ساخته نشد؛ پیشنهاد برای بعد.
2. **دامنه نقش در فرم:** کد شهر یا صف، یا شناسه گره، به‌صورت متن. انتخابگر درخت مرکز ساخته نشد؛ سرویس همان اعتبارسنجی را دارد.
3. **دونفره نبودن دادن نقش** همان رفتار موجود API است و تغییر نکرد (خودی به خود نقش نمی‌دهد؛ بازاحراز TOTP اگر `identity.reauth` روشن است). دونفره کردن آن تصمیم مالک است.
4. **صفحه پیکربندی پرچم‌های هویت** (بخش دیگر م۱۰) ساخته نشد: پرچم‌ها کلیدهای پیکربندی دونفره‌اند و روز راه‌اندازی با API روشن می‌شوند (چک‌لیست).
