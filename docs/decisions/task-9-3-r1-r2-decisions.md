## ۲. یافته: مسیر تغییر موبایل بیمار وجود ندارد

- در کد هیچ مسیری موبایل بیمار را عوض نمی‌کند. `AccountMobileService` صریحاً فقط کارکنان و مرکز را می‌پذیرد («a patient's mobile is their login and is not changed here»).
- موبایل بیمار کلید ورود است. Person ماژول lead هم موبایل خودش را دارد که پیامک‌های ضامن و وام‌گیرنده از آن خوانده می‌شوند.
- **ساختن مسیر تغییر موبایل بیمار** تصمیم کسب‌وکاری و بین‌ماژولی است: یکتایی، Person، رضایت پیامک و پرونده‌های باز. پس در این کار ساخته نمی‌شود.
- **کار انجام‌شده (محتاطانه و افزودنی):** سازوکار پیامک تغییر عامل برای بیمار هم آماده است: قالب `patient`، و ثبت اعلان برای حساب بیمار با آزمون مستقیم. هر مسیر آینده تغییر موبایل بیمار فقط باید `FactorNotices.record` را در تراکنش خودش صدا بزند.
- **پرسش تازه برای مالک:** پ۱ در بخش ۹.

## ۳. R1 — بازاحراز TOTP پیش از کار حساس

### ۳.۱ سازوکار

- **`POST /auth/totp/reauth`** با `{ code }`، فقط برای نشست `active` کارکنان و مرکز (`@SelfService()`؛ بیمار `403`).
  - **یک‌بارمصرف:** همان `totp_last_step` ورود، با به‌روزرسانی شرطی. کدی که برای ورود یا بازاحراز قبلی پذیرفته شده، و هر کد گام زمانی قدیمی‌تر، رد می‌شود. از دو درخواست هم‌زمان با یک کد فقط یکی برنده است.
  - **محدودیت نرخ و قفل:** همان شمارنده خطای TOTP ورود (`staff-totp:<username>`) و شمارنده IP. پس از قفل، کد درست هم با `429` رد می‌شود.
  - **audit:** هر شکست `identity.reauth_failed` (بی کد) و هر موفقیت `identity.reauthenticated`.
  - **نشست عوض نمی‌شود:** فقط `sessions.reauthenticated_at = now` روی **همین** نشست نوشته می‌شود.
- **پنجره:** کار حساس فقط اگر `now − reauthenticated_at ≤ windowSeconds` باشد پذیرفته می‌شود. وگرنه `403 { error: 'reauth_required' }`.
- **ابطال پنجره:**
  - **خروج:** نشست باطل می‌شود و پنجره با آن.
  - **تغییر گذرواژه:** نشست‌های دیگر بسته می‌شوند و `reauthenticated_at` نشست جاری `NULL` می‌شود.
  - **نشست دیگر:** هرگز حساب نمی‌شود، چون پنجره ستون همان ردیف نشست است.
- **اجرای قاعده در لایه سرویس** (قاعده ۱۲):
  - `AuthContext` و `Actor` فیلد `reauthenticatedAt` را از ردیف نشست می‌گیرند. نگهبان همین ردیف را می‌خواند، پس پرس‌وجوی تازه‌ای لازم نیست.
  - `assertFreshMfa(config, actor, now)` در `common/auth/fresh-mfa.ts`. هر سرویس حساس آن را اول صدا می‌زند.
  - **معاف:** actor بی نشست، یعنی CLI (`CLI_ACTOR`) و کارهای سرور. این معافیت صریح آزموده می‌شود.

### ۳.۲ عمل‌های حساس

| عمل | سرویس |
|---|---|
| ساخت نقش، تغییر مجوزهای نقش | `AccessService.createRole`، `setRolePermissions` |
| اعطا و پس‌گرفتن نقش، اعطای نقش منشی | `AccessService.assignRole`، `revokeAssignment`، `assignSecretaryRole` |
| درخواست، تأیید و رد بازنشانی TOTP | `TotpResetService.request`، `approve`، `reject` |
| پیشنهاد، تأیید و رد پیکربندی | `ConfigService.propose`، `decide` |

- تأییدهای دونفره مالی بیرون‌اند (س۲؛ م۳).

### ۳.۳ پنل‌ها

- **`useApi`** (`@sepehr/ui`) یک `fetch` پوشاننده می‌گیرد. پاسخ `403 reauth_required` پنجره «تأیید هویت» را باز می‌کند. پس از بازاحراز موفق، همان درخواست **یک بار** دوباره فرستاده می‌شود. انصراف کاربر همان خطا را برمی‌گرداند. هیچ داده‌ای در `localStorage` نمی‌رود.
- پنجره در `ApiProvider` هر دو پنل (ادمین و مرکز) نصب می‌شود.
- **تأیید بصری مالک** لازم است.

## ۴. س۳ — موبایل تأییدشده برای کاربران پنل داخلی

- **دامنه:** حساب‌های `kind = 'staff'`. حساب مرکز همان قاعده ۴-۶ را دارد (مدیر مرکز).
- **اعمال در نگهبان (سخت‌تر شد، دستور مالک ۱۴۰۵/۰۷/۱۸):** نشست `active` کارمند بی موبایل تأییدشده فقط به مسیرهای `@AllowWithoutMobile()` می‌رسد. هر مسیر دیگر، حتی خودخدمت (نشست‌ها، گذرواژه، مجوزهای خود، بازاحراز)، پاسخ `403 { error: 'mobile_required' }` می‌گیرد. هیچ حسابی قفل یا غیرفعال نمی‌شود.
  - **مسیرهای مجاز (دقیقاً شش؛ آزمون فهرست را قفل می‌کند):** `GET /auth/mobile`، `POST /auth/mobile/request`، `POST /auth/mobile/verify`، `POST /auth/logout`، `POST /auth/logout-all` و `GET /auth/me`.
  - **چرا `me` هم:** پنل از `me.mobileRequired` می‌فهمد که باید فرم اجباری را نشان دهد. `me` فقط وضعیت نشست خود کاربر را می‌دهد. ادمین در این حالت `/access/me` را نمی‌خواند.
- **`GET /auth/me`** فیلد `mobileRequired` را برمی‌گرداند. پنل ادمین در این حالت فقط فرم اجباری تأیید موبایل را نشان می‌دهد (همان فرم دومرحله‌ای ۴-۶).
- **پرچم:** `identity.staff_mobile_required` = `{ enabled: false }`.

## ۵. R2 — پیامک هنگام تغییر عامل ورود

### ۵.۱ رخدادها

| رخداد | گیرنده | قالب |
|---|---|---|
| تغییر گذرواژه | موبایل تأییدشده حساب | `identity.factor.password_changed` (staff) |
| تأیید بازنشانی TOTP | موبایل تأییدشده حساب هدف | `identity.factor.totp_reset` (staff) |
| ثبت TOTP تازه (نخستین `verifyTotp` پس از بازنشانی) | موبایل تأییدشده حساب | `identity.factor.totp_enrolled` (staff) |
| تغییر موبایل تأییدشده کارکنان و مرکز | **موبایل تأییدشده قبلی** | `identity.factor.mobile_changed` (staff) |
| تغییر موبایل بیمار (مسیر ندارد؛ بخش ۲) | موبایل قبلی | `identity.factor.patient_mobile_changed` (patient) |

- نخستین ثبت TOTP پس از ساخت حساب، و نخستین تأیید موبایل، پیامک ندارند. چیزی عوض نشده و موبایل قبلی هم نیست.
- **متن ثابت، بی فیلد شخصی.** متن در DB است و از پنل پیامک قابل‌تغییر. دسته `urgent` است.

### ۵.۲ مسیر (outbox، پس از commit)

1. در تراکنش تغییر عامل: یک ردیف در جدول تازه **`factor_change_notices`** (ماژول identity؛ فقط‌افزودنی)، و رویداد outbox `identity.factor_changed` با `{ noticeId }`. موبایل در payload رویداد نیست (قاعده ۳۰).
2. پس از commit: worker رویداد را به مصرف‌کننده `identity.factor_notice` می‌دهد. مصرف‌کننده ردیف را می‌خواند و `NotificationsPort.send` را صدا می‌زند، با کلید عدم تکرار `identity.factor:<noticeId>`. پیامک در `sms_dispatches` ثبت و با صف پیامک فرستاده می‌شود.
3. **شکست:** اگر ثبت یا ارسال پیامک شکست بخورد، تغییر عامل سر جایش می‌ماند. رویداد outbox با backoff نمایی تا ۸ بار تکرار می‌شود و خطای آن در `outbox_events.last_error` و هشدار worker می‌ماند. ارسال خود پیامک هم تلاش دوباره صف پیامک را دارد.
4. **بی موبایل تأییدشده:** ردیفی ساخته نمی‌شود. فقط audit `identity.factor_notice_skipped` ثبت می‌شود (`no_verified_mobile`) و تغییر عامل انجام می‌شود.
5. **پرچم خاموش:** ردیف ساخته می‌شود و مصرف‌کننده آن را بی پیامک کنار می‌گذارد (`skipped_flag_off` در audit). این‌طور سابقه هست و روشن کردن پرچم پیامک کهنه نمی‌فرستد.

- **پرچم:** `identity.factor_change_sms` = `{ enabled: false }`.

## ۷. مهاجرت `0080_staff_reauth_and_factor_notices` (فقط افزودنی)

**خلاصه SQL (پیش از اجرا):**

```sql
ALTER TABLE "sessions" ADD COLUMN "reauthenticated_at" timestamptz;   -- nullable، بی پیش‌فرض
CREATE TABLE "factor_change_notices" (
  id uuid PK DEFAULT uuidv7(), account_id uuid NOT NULL REFERENCES user_accounts(id),
  event text NOT NULL CHECK (event IN ('password_changed','totp_reset','totp_enrolled',
                                       'mobile_changed','patient_mobile_changed')),
  audience text NOT NULL CHECK (audience IN ('staff','patient')),
  mobile text NOT NULL CHECK (mobile ~ '^9[0-9]{9}$'),
  created_at timestamptz NOT NULL DEFAULT now()   -- فقط‌افزودنی: بی updated_at و deleted_at
);
CREATE INDEX factor_change_notices_account_idx ON factor_change_notices (account_id);
CREATE TRIGGER factor_change_notices_append_only BEFORE UPDATE OR DELETE … reject_append_only_change();
REVOKE UPDATE, DELETE ON factor_change_notices FROM sepehr_app;
GRANT SELECT, INSERT ON factor_change_notices TO sepehr_app;
INSERT INTO config_keys: identity.reauth، identity.factor_change_sms، identity.staff_mobile_required (technical، sensitive)
INSERT INTO config_values: سه مقدار اولیه خاموش (جدول ۶)
INSERT INTO sms_templates: پنج قالب (۴ staff و ۱ patient)، نسخه ۱، دسته urgent
```

- **بی تغییر در قید یا تابع موجود.** هیچ جدول مالی لمس نمی‌شود.
- **پیش از اجرا روی پایگاه محلی:** `pg_dump` در `D:\sepehr_app\db-backups`، نشان دادن به مالک، سپس اجرا، بررسی فقط‌خواندنی و `bash scripts/ci/db-drift.sh`.
