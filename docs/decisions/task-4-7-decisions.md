# تسک ۴-۷ — صفحات دریافت خدمت

**وضعیت:** فقط نقشه (۱۴۰۵/۰۷/۱۳)، به خواست مالک. **منتظر تأیید.** هیچ کد، مهاجرت یا commit کدی نیست.

**نوع:** غیرمالی. فقط صفحه روی APIهای موجود ۴-۵ و ۴-۶. هیچ ثبت، قاعده مالی یا تغییری در ledger، wallet، اقساط یا service نیست.

**مرجع:**
- سند ۱۳ (۴-۷) و سند ۱۲ §۵ و §۶.
- سند ۰۸ (سیستم طراحی، تقویم شمسی واحد).
- واژه‌نامه ۰۱: «کیف اعتبار»؛ هرگز «کیف پول».
- پاسخ‌های مالک ۴-۶ (پ۲: پزشک فقط نام و مجاز/غیرمجاز).

## متن تسک (سند ۱۳)

```
- پنل پزشک/منشی: بیماران شارژشده معرفی‌شده به او (فقط سقف قابل استفاده نزد
  خودش)، صدور مجوز خدمت، ورود کد، تاریخچه خدمات.
- بیمار: کیف اعتبار (عنوان از پیکربندی، پیش‌فرض «کیف اعتبار»)، تاریخچه
  مصرف، اقساط شمسی.
```

**پذیرش:**
- Playwright برای «شارژ ← مجوز ← کد ← ثبت ← قطعی شدن».
- هیچ متن «کیف پول» در خروجی build نباشد.

## آنچه امروز هست (بررسی فقط‌خواندنی)

- **API آماده:**
  - **شارژ (۴-۵):** `/funding/requests` (درخواست، فهرست، تأیید، رد) و `/me/funding/:applicationId` (کیف و اقساط بیمار).
  - **خدمت (۴-۶):** `/service/patients`، `/service/authorizations` (صدور، فهرست، جزئیات، ارسال دوباره کد، ثبت با کد، لغو مالی) و `/me/service/authorizations`.
  - **موبایل (۴-۶):** `/auth/mobile` (وضعیت، درخواست کد، تأیید).
- **صفحه‌ای برای هیچ‌کدام نیست.**
  - **صفحه‌های شارژ** در نقشه ۴-۵ آمده بود («درخواست شارژ در `/completion/[id]`، صف تأیید مالی، کیف و اقساط در `/me/credit/[id]`»)، ولی ۴-۵ فقط API ساخت.
  - **بی صفحه شارژ،** گام اول مسیر پذیرش Playwright («شارژ») با مرورگر شدنی نیست.
- **صفحه ثبت موبایل حساب** (نقشه ۴-۶، مرحله ۲: «صاحب حساب در پنل خودش») هم نیست. بی آن، پزشک تازه از UI قابل اتصال نیست؛ فقط از داده آزمون.
- **پنل مرکز:** `/panel/*` با `nav.ts` (بخش‌ها با مجوز)، و الگوی صفحه‌های پیش‌فاکتور برای پزشک و منشی.
- **پنل داخلی:** `/completion/[id]` و `/receipts` (۴-۴).
- **بیمار:** `/me/credit/[id]` (قرارداد و تکمیل، ۴-۴).
- **e2e:** کدهای ورود را از چاپ پیامک توسعه (`login code for`) می‌گیرد. کد خدمت پیامک متنی است (`text for … : …`) و امروز جمع نمی‌شود.
- **پیکربندی عنوان کیف** (`wallet.purse_title` یا مانند آن) وجود ندارد.

  - **endpoint عمومی خواندنی کوچک** برای عنوان، یا افزودن عنوان به `myFundingView`. **س۴.**

### ۵. آزمون‌ها

- **Playwright، spec تازه `service-path.spec.ts`:**
  - **شارژ:** از پرونده تکمیل‌شده (گام‌های مشترک با `completion-path`، استخراج‌شده در `credit-steps.ts`)، درخواست شارژ در `/completion/[id]` و تأیید شارژ در `/funding` با مالیِ دیگر.
  - **مجوز:** پزشک در `/panel/patients` بیمار را «مجاز» می‌بیند (بی هیچ مبلغی) و یک ردیف را مجوز می‌دهد.
  - **کد:** از چاپ پیامک توسعه خوانده می‌شود.
  - **ثبت و قطعی شدن:** وضعیت «قطعی شد» (`finalize_after_hours = 0`).
  - **بیمار:** در کیف اعتبار، مانده کم‌شده، مصرف ثبت‌شده و اقساط شمسی را می‌بیند.
  - **همه صفحه‌ها:** `checkPage` (فقط شمسی، دسترس‌پذیری بی تخلف جدی).
- **e2e زیرساخت:**
  - **کد خدمت:** `stack.ts` علاوه بر `login code for` خطوط `text for` را هم با الگوی کد خدمت جمع می‌کند (`.stack/service-codes.json`).
  - **موبایل پزشک:** seed حساب پزشک را از قبل تأییدشده دارد (۴-۶). یک گام e2e هم صفحه «حساب من» را با کد واقعی می‌سنجد، روی حساب منشی یا حساب مرکز تازه.
- **«کیف پول»:** اسکریپت پذیرش (`scripts/ci/no-wallet-wording.sh` در lint) که خروجی build وب و ادمین (`.next`) و منبع را برای «کیف پول» جست‌وجو می‌کند و با یافتن، شکست می‌خورد.
- **unit و integration:**
  - پیام‌های خطای تازه.
  - guard پیکربندی `wallet.purse_title`.
  - اگر س۴ «افزودن به `myFundingView`» باشد، آزمون integration آن.
- **performance.spec:** افزودن مسیرهای تازه بیمار و پنل به فهرست زمان بارگذاری، مثل ۴-۴.

## پرسش‌ها از مالک

- **س۱ — نمایش به پزشک:**
  - **ناسازگاری:** سند ۱۳ می‌گوید «فقط سقف قابل استفاده نزد خودش» (یعنی مبلغ). پاسخ شما در ۴-۶ (پ۲) می‌گوید «فقط نام و مجاز/غیرمجاز؛ بدون مبلغ، مانده یا امتیاز». API ساخته‌شده هم همین است.
  - **پیش‌فرض: پاسخ پ۲** (بی مبلغ). پزشک فقط مبلغ ردیف‌هایی را می‌بیند که خودش مجوز می‌دهد، و اگر از مانده بیشتر باشد رد صریح می‌گیرد.
- **س۲ — صفحه‌های شارژ ۴-۵** (درخواست در `/completion/[id]` و صف `/funding` مالی) در همین تسک ساخته شوند؟
  - **پیش‌فرض: بله.** بی آن‌ها پذیرش Playwright («شارژ ← …») شدنی نیست، و در نقشه ۴-۵ آمده بودند.
- **س۳ — صفحه لغو مالی** (`/services` در پنل داخلی) در ۴-۷ یا ۴-۸؟
  - **پیش‌فرض: در ۴-۷،** فهرست و «لغو با دلیل» روی API موجود. ۴-۸ عملیات ویژه کیف است، نه لغو تک‌مجوز.
- **س۴ — عنوان کیف از پیکربندی:**
  - **گزینه الف (پیشنهاد):** فیلد `purseTitle` در پاسخ موجود `/me/funding/:applicationId`.
  - **گزینه ب:** endpoint عمومی `GET /config/public/purse-title`.
  - **هر دو:** کلید تازه `wallet.purse_title` با مهاجرت فقط‌افزودنی `0038` (داده پیکربندی).
- **س۵ — «حساب من» با ثبت موبایل:** فقط در پنل مرکز (پزشک، مدیر مرکز، منشی)، یا در پنل داخلی هم برای کارکنان؟
  - **پیش‌فرض: پنل مرکز.** الزام فقط برای پزشک و مدیر مرکز است.

## پاسخ مالک (۱۴۰۵/۰۷/۱۳): نقشه تأیید شد

1. **س۱:** پزشک فقط نام و مجاز/غیرمجاز می‌بیند، بی مبلغ یا مانده کیف. مبلغ هر مجوز را فقط هنگام صدور، از ردیف‌های پیش‌فاکتور، می‌بیند.
2. **س۲:** صفحه‌های شارژ ۴-۵ در همین تسک ساخته شوند.
3. **س۳:** صفحه لغو مالی در ۴-۷، فقط پیش از قطعی شدن، با پیام فارسی `service_final`.
4. **س۴:**
   - عنوان کیف از فیلد تازه `purseTitle` در `/me/funding`، با کلید `wallet.purse_title`.
   - اسکریپت lint ظهور «کیف» با «پول» را در خروجی build رد کند.
5. **س۵:** «حساب من» فقط در پنل مرکز.

**افزوده‌ها:**
- **پیام خوداعتمادی:** پیام UI «تأییدکننده نمی‌تواند درخواست خودش را تأیید کند»، و Playwright آن را بسنجد.
- **کد خدمت:** فقط در جایگاه لازم دیده شود، نه در لاگ.
- **مهاجرت `0038`:** پیش از آن `pg_dump`، خلاصه SQL و پرسش.
- **۴-۶b:** کامل شده بود (`e15aadd`)، پیش از شروع ۴-۷.

## وضعیت پیشرفت (اجرا، ۱۴۰۵/۰۷/۱۳)

### بک‌اند (افزوده‌های غیرمالی)

- **`purseTitle` در `GET /me/funding/:applicationId`:**
  - از کلید تازه `wallet.purse_title`.
  - **guard:** عنوان با «کیف» و «پول» کنار هم (با فاصله یا نیم‌فاصله) رد می‌شود. عبارت در کد از دو کلمه ساخته می‌شود تا در build نیاید.
  - **دو تغییر کوچک در فایل‌های ۴-۵:**
    - **سرویس:** `FundingService` حالا `CONFIG` را هم می‌گیرد؛ یک فیلد نمایشی است، بی اثر بر هیچ ثبت.
    - **آزمون:** آزمون آرامش ۴-۵ که این سرویس را دستی می‌سازد، یک آرگومان (`CONFIG`) گرفت؛ هیچ ادعایی عوض نشد.
- **`GET /service/patients/:purseId/lines`** (ماژول `service`، فقط خواندن):
  - **داده:** ردیف‌های پیش‌فاکتور با نام خدمت، تعداد، مبلغ، و «در مجوز زنده».
  - **حذف‌شده:** مانده کیف (پ۲).
  - **دسترسی:** پزشک غیرمعرفی‌شده ۴۰۴ (همان IDOR).
- **مهاجرت `0038_purse_title`:** داده پیکربندی، بی جدول.

### صفحه‌ها

- **پنل مرکز:**
  - `/panel/patients`: نام و مجاز/غیرمجاز.
  - `/panel/patients/[purseId]`: انتخاب ردیف‌ها، جمع ریالی و تومانی.
  - `/panel/authorizations/[id]`: وضعیت و ورود کد. کد پس از هر تلاش از فیلد پاک می‌شود و هرگز نمایش، نگه‌داری یا لاگ نمی‌شود. ارسال دوباره با شمارش ۶۰ ثانیه.
  - `/panel/authorizations`: تاریخچه.
  - `/panel/account`: «حساب من»، تأیید موبایل با کد. در همه حساب‌ها دیده می‌شود (بخش بی‌مجوز).
- **پنل داخلی:**
  - **بخش «شارژ کیف اعتبار» در `/completion/[id]`:**
    - درخواست؛ و وضعیت (در انتظار، شارژشده، یا ردشده با دلیل).
    - تأیید برای مالیِ دیگر.
    - برای درخواست‌دهنده، به‌جای دکمه پیام «تأییدکننده نمی‌تواند درخواست خودش را تأیید کند.».
  - **`/funding`:** صف تأیید مالی، با همان پیام برای درخواستِ خود. پاسخ ۴۰۹ `same_person` API هم در این صفحه همین پیام را نشان می‌دهد.
  - **`/services`:** لغو با دلیل فقط برای «منتظر کد» و «ثبت‌شده»؛ `service_final` پیام فارسی دارد.
- **بیمار** (`/me/credit/[id]`): بخش کیف با عنوان از پیکربندی؛ قابل استفاده (ریال و تومان)، تاریخچه مصرف (تاریخ، مرکز، مبلغ، وضعیت؛ بی شرح درمان)، و اقساط شمسی.
- **پیام‌های فارسی** همه کدهای خطای ۴-۵ و ۴-۶ در `errors.ts`.

### آزمون و پذیرش
