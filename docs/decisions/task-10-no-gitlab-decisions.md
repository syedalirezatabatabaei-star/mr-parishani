دستور مالک: «GitLab فعلاً نداریم؛ کارهای فاز ۱۰ را که بدون GitLab و ابر داخلی ممکن است انجام بده (runbookها، چک‌لیست‌ها، مانیتورینگ، آماده‌سازی ۹-۵)، و بقیه را با دلیل مسدودی فهرست کن.» و: «سؤال شش commit مالی فازهای ۱ و ۲ و ترتیب git بعدی را عیناً با گزینه‌ها و پیشنهاد خودت بیاور، بدون اجرا.»

## ۱. سؤال گیت (ت۱۱): بدون اجرا

**سؤال:** اسناد ۱۳ و ۱۹ می‌گویند commitهای [مالی] «حتی پس از گیت را انجام بده» تا GitLab و بازبین انسانی push نشوند. آیا این قاعده شامل ۶ commit کد مالی فاز ۱ و ۲ هم می‌شود که وسط تاریخچه‌اند؟ جدا کردنشان بازنویسی تاریخچه می‌خواهد. **پیش از دستور گیت بعدی لازم است.**

**واقعیت امروز (بررسی فقط‌خواندنی، ۱۴۰۵/۰۷/۲۴):**
- `main` محلی **۲۶۸ commit** جلوتر از تنها remote است: `github-old` (GitHub؛ آخرین push `f51af6f`، ۲۰۲۶-۰۹-۲۷، PR شماره ۵ فاز ۰). عقب‌تر نیست.
- **۶ commit کد مالی فاز ۱ و ۲:** `298b302` (دفتر کل، ۱-۱)، `b783e7b` (کیف، ۱-۲)، `86238ce` (اقساط، ۱-۳)، `0c1668f` (تطبیق شبانه، ۱-۴)، `3c68262` و `ef50612` (فاز ۲، فقط `repayment.service.ts`). به‌علاوه ۲ commit سند مالی: `59efa83` و `fec64d4` (سند ۰۲). هیچ‌کدام push نشده‌اند.
- **دامنه واقعی بزرگ‌تر است:** ۴۹ commit از ۲۶۸ ماژول‌های مالی را لمس می‌کنند (ledger، wallet، repayment، settlement، collection، instrument، contract)، پراکنده در فاز ۱ تا ۹.
- **اولین commit push‌نشده خودش مالی است** (`298b302`). پس هیچ بخش غیرمالی از ابتدای صف را نمی‌توان بی commit مالی push کرد.
- کد غیرمالی بعدی به ماژول‌های مالی وابسته است (تسویه، اعتبار، قرارداد)؛ تاریخچه بی commitهای مالی build نمی‌شود.
- دو stash محلی (`wip-r18-advisor-own-scope`، `wip-4-5-before-limit`) هرگز push نمی‌شوند.

**گزینه‌ها:**

| گزینه | چه | پیامد |
|---|---|---|
| **الف** | وقتی GitLab آماده شد، کل تاریخچه **بی تغییر** به یک شاخه واردات غیرمحافظت‌شده push شود؛ `main` محافظت‌شده آن را فقط با merge request و CI سبز و **تأیید ثبت‌شده بازبین انسانی برای فایل‌های مالی** می‌گیرد. قاعده «commit مالی بی بازبینی ادغام نشود» در **ادغام** اعمال می‌شود، نه در push. | بی بازنویسی؛ همه hashها (RESUME، تصمیم‌ها، bundleها) درست می‌مانند. بسته بازبینی: فهرست ۴۹ commit و فایل‌ها، خلاصه، ریسک، آزمون‌ها (سند ۱۹ §۱۰-۰). |
| **ب** | بازنویسی تاریخچه: commitهای مالی جدا و دیرتر. | همه hashها عوض می‌شوند؛ ارجاع‌های RESUME و تصمیم‌ها می‌شکنند؛ تاریخچه غیرمالی بی کد مالی build نمی‌شود. **پیشنهاد نمی‌شود.** |
| **ج** | تا GitLab و بازبین هیچ push (وضع فعلی). | امن؛ ریسک فقط از دست رفتن دستگاه، که با bundle روی `D:` و کپی بیرونی (کار مالک) پوشش دارد. |
| **د** | push بخش غیرمالی به `github-old` همین حالا. | ممکن نیست بی بازنویسی (اولین commit مالی است)، و GitHub سرویس بیرونی است؛ مالک push و remote را ممنوع کرده (دور یازدهم). **پیشنهاد نمی‌شود.** |

**پیشنهاد من:** **ج تا آماده شدن GitLab، سپس الف.** پاسخ ت۱۱: «بله، شامل commitهای مالی فاز ۱ و ۲ هم هست؛ ولی قاعده در ادغام به `main` محافظت‌شده اعمال می‌شود، نه با بازنویسی تاریخچه.»

**تصمیم مالک (۱۴۰۵/۰۷/۲۴، دور بیست‌ودوم): گزینه «ج» اکنون (هیچ push)، و گزینه «الف» وقتی GitLab آماده شد.**
- پاسخ ت۱۱: قاعده شامل commitهای مالی فاز ۱ و ۲ هم هست، و در **ادغام** به `main` محافظت‌شده اعمال می‌شود؛ تاریخچه بازنویسی نمی‌شود.
- تا دستور «GitLab آماده است»: هیچ push، هیچ remote تازه، هیچ تغییر در `github-old`. bundleها روی `D:` تنها نسخه بیرون از درخت کارند.
- با «GitLab آماده است» و سپس «گیت را انجام بده»: همان ترتیب پایین، گام به گام، و ادغام فقط پس از تأیید مالک.

**ترتیب پیشنهادی گیت بعدی (فقط با دستور «GitLab آماده است» و سپس «گیت را انجام بده»؛ هیچ‌کدام امروز اجرا نشد):**
1. bundle تازه (`git bundle create D:\sepehr-backup\repo-<زمان>.bundle --all`، `git bundle verify`) و `pg_dump` روی `D:`.
2. افزودن remote GitLab (نام `gitlab`). به `github-old` push نمی‌شود؛ حذف آن فقط با دستور مالک.
3. push `f51af6f` به `main` GitLab (همان فاز ۰ که در GitHub ادغام شده بود)، و محافظت `main`: ادغام فقط با CI سبز و تأیید بازبین.
4. push کل `main` محلی به شاخه `import/history-1405-07` (بی بازنویسی، بی force).
5. یک merge request از آن به `main`؛ CI GitLab باید سبز شود (پذیرش ۱۰-۰: یک MR آزمایشی با CI قرمز رد شود).
6. بسته بازبینی مالی (فهرست ۴۹ commit و فایل‌های مالی، خلاصه، ریسک و آزمون‌ها) برای بازبین؛ تأیید او در MR ثبت شود.
7. ادغام فقط پس از تأیید مالک. stashها محلی می‌مانند.
