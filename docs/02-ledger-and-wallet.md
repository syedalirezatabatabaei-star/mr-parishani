# ۰۲ — دفتر کل، کیف اعتبار و اقساط

پرریسک‌ترین بخش سامانه. هیچ کد مالی بدون خواندن کامل این سند نوشته نشود.

## ۱. قواعد پایه

1. واحد ذخیره: **ریال**، نوع `bigint`. هرگز اعشار، هرگز تومان.
2. هر رویداد مالی یک `JournalEntry` است که از دو یا چند `LedgerEntry` تشکیل می‌شود و **جمع بدهکار و بستانکار آن دقیقاً برابر است**.
3. `ledger_entry` فقط `INSERT` می‌پذیرد. کاربر برنامه مجوز `UPDATE` و `DELETE` ندارد (`REVOKE` در مهاجرت).
4. اصلاح = `ReversalEntry` با ارجاع به سند اصلی، نه ویرایش.
5. هر عملیات مالی `idempotency_key` یکتا دارد. تکرار همان کلید، همان نتیجه را برمی‌گرداند و سند جدید نمی‌سازد.
6. عملیات روی یک کیف اعتبار داخل تراکنش با `SELECT ... FOR UPDATE` روی ردیف کیف اجرا می‌شود.
7. هر سند `entity_id` دارد؛ در نسخه اول همیشه `aramesh`.

## ۲. ساختار جدول‌ها (طرح اولیه)

```sql
ledger_account (
  id uuid pk, entity_id text, code text, name text,
  kind text check (kind in ('asset','liability','income','expense','memo')),
  owner_type text,  -- borrower | doctor | center | company
  owner_id uuid, currency text default 'IRR'
)

journal_entry (
  id uuid pk, entity_id text, event_type text, occurred_at timestamptz,
  case_id uuid, credit_application_id uuid, idempotency_key text unique,
  reverses_journal_entry_id uuid null, created_by uuid, reason text
)

ledger_entry (
  id uuid pk, journal_entry_id uuid, account_id uuid,
  direction text check (direction in ('debit','credit')),
  amount_rial bigint check (amount_rial > 0), created_at timestamptz
)
-- پارتیشن ماهانه بر اساس created_at
```

**نماهای محاسباتی:** مانده هر حساب از جمع ثبت‌ها. برای کارایی، نمای مادی‌شده `account_balance` که با رویداد به‌روزرسانی می‌شود، اما **منبع حقیقت همیشه جمع ثبت‌هاست** و کار تطبیق شبانه این دو را مقایسه می‌کند.

## ۳. حساب‌های منطقی کیف اعتبار

| حساب | کاربرد |
|---|---|
| `purse.approved` | سقف اعتبار مصوب پرونده |
| `purse.available` | مانده قابل مصرف |
| `purse.reserved` | مبلغ رزروشده برای یک مجوز خدمت |
| `purse.consumed_pending` | خدمت ثبت‌شده در انتظار قطعی شدن |
| `borrower.debt` | طلب شرکت از وام‌گیرنده (اصل + کارمزد طبق قرارداد) |
| `doctor.payable` | بدهی شرکت به پزشک |
| `doctor.fee_receivable` | کارمزد قابل دریافت از پزشک (اعتباری و نقدی) |
| `company.fee_income` | درآمد کارمزد و هزینه تشکیل پرونده (آرامش) |
| `bank.settlement` | حساب بانکی پرداخت به پزشکان |
| `bank.collection` | حساب دریافت اقساط |
| `suspense.unallocated` | پرداخت دریافت‌شده در انتظار تخصیص |
| `downpayment.held` | پیش‌پرداخت وام‌گیرنده نزد آرامش، از تأیید فیش تا شارژ کیف (ADR-034) |
| `downpayment.refund_payable` | پیش‌پرداخت مصرف‌نشده و ابطال‌شده، بدهی آرامش به وام‌گیرنده تا استرداد (ADR-036) |
| `fee.refund_payable` | هزینه تشکیل پرونده و کارمزد طرحِ پرداخت‌شده‌ی پرونده‌ای که پیش از شارژ باطل شد، بدهی آرامش به وام‌گیرنده تا استرداد (ADR-036، ۴-۸) |

### نوع حساب‌ها (رسمی، ۱۴۰۵/۰۷/۰۵)

این دفتر کل **دفتر خود شرکت (آرامش)** است؛ هر حساب از منظر شرکت خوانده می‌شود، نه از منظر بیمار.

| نوع (`kind`) | حساب‌ها | مانده عادی |
|---|---|---|
| `asset` | `borrower.debt`، `doctor.fee_receivable`، `bank.settlement`، `bank.collection` | بدهکار |
| `liability` | `doctor.payable`، `downpayment.held`، `downpayment.refund_payable`، `fee.refund_payable` | بستانکار |
| `income` | `company.fee_income` | بستانکار |
| `memo` | `purse.approved`، `purse.available`، `purse.reserved`، `purse.consumed_pending`، `suspense.unallocated` | زنجیره کیف: بستانکار |

حساب‌های `purse.*` ردیابی داخلی کیف اعتبارند. مانده بستانکارشان در طول زنجیره (مصوب ← قابل مصرف ← رزرو ← در انتظار قطعی) جابه‌جا می‌شود و در پایان هر پرونده صفر است؛ طرف واقعی آن‌ها `borrower.debt` در تصویب و ابطال، و `doctor.payable` در قطعی شدن است.

## ۴. رویدادهای مالی

هر ردیف یک `JournalEntry` است.

| رویداد | بدهکار | بستانکار |
|---|---|---|
| تصویب اعتبار | `borrower.debt` (تعهد) | `purse.approved` |
| شارژ کیف اعتبار | `purse.approved` | `purse.available` |
| دریافت هزینه تشکیل پرونده | `bank.collection` | `company.fee_income` |
| دریافت پیش‌پرداخت (تأیید فیش، ۴-۳ و ۴-۵) | `bank.collection` | `downpayment.held` |
| تصویب اعتبار با پیش‌پرداخت (هنگام شارژ، ۴-۵) | `borrower.debt` (وام A) و `downpayment.held` (پیش‌پرداخت D) | `purse.approved` (A + D) |
| کارمزد طرح (هنگام ساخت برنامه اقساط) | `borrower.debt` | `company.fee_income` |
| رزرو برای مجوز خدمت | `purse.available` | `purse.reserved` |
| لغو رزرو | `purse.reserved` | `purse.available` |
| ثبت خدمت (کد پیامکی بیمار) | `purse.reserved` | `purse.consumed_pending` |
| قطعی شدن خدمت | `purse.consumed_pending` | `doctor.payable` |
| کارمزد خدمت اعتباری | `doctor.fee_receivable` | `company.fee_income` |
| کارمزد خدمت نقدی | `doctor.fee_receivable` | `company.fee_income` |
| پرداخت صورت‌وضعیت پزشک | `doctor.payable` | `bank.settlement` |
| تهاتر کارمزد در صورت‌وضعیت | `doctor.payable` | `doctor.fee_receivable` |
| دریافت قسط | `bank.collection` | `borrower.debt` |
| فیش در انتظار تأیید | `bank.collection` | `suspense.unallocated` |
| تخصیص فیش تأییدشده به اقساط (تسک ۱-۳) | `suspense.unallocated` | `borrower.debt` |
| ابطال مانده مصرف‌نشده، بخش وام (کامل یا بخشی، ۴-۸) | `purse.available` | `borrower.debt` |
| ابطال مانده مصرف‌نشده، بخش پیش‌پرداخت (۴-۸) | `purse.available` | `downpayment.refund_payable` |

| انصراف پیش از شارژ: استرداد هزینه تشکیل یا کارمزد طرحِ پرداخت‌شده (۴-۸) | `company.fee_income` | `fee.refund_payable` |
| انصراف پیش از شارژ: استرداد پیش‌پرداخت (۴-۸) | `downpayment.held` | `downpayment.refund_payable` |
| پرداخت استرداد هزینه‌ها (۴-۸) | `fee.refund_payable` | `bank.settlement` |
| خسارت انصراف (یکجا، با سررسید جدا در `repayment_charges`؛ ۴-۸) | `borrower.debt` | `company.fee_income` |
| بخشودن کارمزد اقساط سررسیدنشده در انصراف پس از شارژ (۴-۸) | `company.fee_income` | `borrower.debt` |
| اصلاح | سند معکوس کامل | |

**اصلاح جدول (۱۴۰۵/۰۷/۰۵، تأیید مالک):** جهت ثبت‌ها از منظر شرکت بازنویسی شد (ADR-017). چهار سطر به تصمیم صریح مالک عوض شد: تصویب اعتبار، قطعی شدن خدمت، تهاتر کارمزد و ابطال مانده مصرف‌نشده. جهت چهار سطر زنجیره کیف (شارژ، رزرو، لغو رزرو، ثبت خدمت) هم به‌تبع آن برگشت، چون بدون آن زنجیره بسته نمی‌شد (`purse.approved` در شارژ دوباره بستانکار می‌شد). حساب‌های هر سطر همان قبلی‌اند. درستی جدول با یک پرونده کامل سنجیده شد: هر سند تراز است، زنجیره کیف و حساب‌های پزشک صفر می‌شوند و فقط طلب از وام‌گیرنده می‌ماند.

**کارمزد طرح (۱۴۰۵/۰۷/۰۵، تأیید مالک):** جدول قبلی سطری برای کارمزد طرح نداشت، در حالی که `borrower.debt` «اصل + کارمزد طبق قرارداد» است (بخش ۳). کارمزد طرح (`PlanFee`) هنگام ساخت برنامه اقساط با یک سند جدا ثبت می‌شود و مبلغ کل اقساط اصل به‌علاوه همین کارمزد است. درآمد آن **فوری** شناسایی می‌شود؛ سرشکن کردن آن روی اقساط `TODO(decision)` است. این با «هزینه تشکیل پرونده» (`OriginationFee`) فرق دارد، که نقدی و جدا دریافت می‌شود.

**فیش در انتظار تأیید (۱۴۰۵/۰۷/۰۵، تأیید مالک):** پول دریافت‌شده بلافاصله در `bank.collection` ثبت و در برابرش در `suspense.unallocated` نگه داشته می‌شود؛ پس از تأیید مالی، در تسک ۱-۳ از `suspense.unallocated` به `borrower.debt` منتقل می‌شود. پرداخت اضافه تا تعیین تکلیف در همان `suspense.unallocated` می‌ماند (بخش ۵).

**پیش‌پرداخت (۱۴۰۵/۰۷/۱۱، تأیید مالک، ADR-034):**

- **نگهداری:** پیش‌پرداخت از تأیید فیشش در `downpayment.held` نگه داشته می‌شود؛ این بدهی آرامش به وام‌گیرنده است.
- **کلید ثبت:** `contract:receipt:<receiptId>`. ارجاع `credit_application_id` روی سند است، و پیوندش در جدول `down_payment_postings`.
- **ثبت عطف‌به‌ماسبق:** فیش‌های پیش‌پرداختی که در ۴-۳ بی‌ثبت تأیید شده بودند، با **همین کلید** `contract:receipt:<receiptId>` ثبت می‌شوند.
  - **مسیر:** فرمان `contract:post-down-payments`، یا هنگام شارژ.
  - **idempotent:** اجرای دوباره سند دوم نمی‌سازد.
- **هنگام شارژ:** پیش‌پرداخت وارد زنجیره کیف می‌شود. زنجیره `purse.*` آن پرونده A + D است، و قید «مصرف ≤ مصوب» با سقف A + D سنجیده می‌شود.
- **بدهی وام‌گیرنده:** فقط A به‌علاوه کارمزد طرح. D = 0 یعنی همان سطر «تصویب اعتبار».
- **برگشت پیش از شارژ:** فقط با سند معکوس کامل (سطر «اصلاح»)، توسط مالی و با دلیل. پس از شارژ، برگشت فقط از مسیر انصراف (بخش ۶) است.
- **ترتیب مصرف:** اول پیش‌پرداخت، بعد وام. اثرش فقط در ابطال مانده است: پیش‌پرداخت مصرف‌نشده مسترد می‌شود و فقط بخش وامِ مصرف‌نشده از `borrower.debt` کم می‌شود.
- **کارمزد طرح:** سند کارمزد طرح به پرونده اعتباری ارجاع می‌دهد، تا در گروه درمانِ با Case مشترک هر عضو جدا شناخته شود.

**ابطال مانده و استرداد (۱۴۰۵/۰۷/۱۳، تأیید مالک، ADR-036):**

- **مبلغ:** ابطال کامل یا بخشی است و هرگز بیش از مانده مصرف‌نشده نیست.
- **تقسیم:** مانده مصرف‌نشده به ترتیب ADR-034 تقسیم می‌شود؛ مصرف اول از پیش‌پرداخت است و ابطال اول از وام.
  - **بخش وام:** بدهی را کم می‌کند.
  - **بخش پیش‌پرداخت:** بدهی نیست و به `downpayment.refund_payable` می‌رود تا مسترد شود.
- **اقساط:** بخش وام از آخرین قسطِ بی‌پرداخت به عقب کم می‌شود، با نسخه تازه برنامه، نه UPDATE (بخش ۵).
- **اصلاح:** فقط با سند معکوس.

**قیدهای غیرقابل عبور (در کد، نه در پیکربندی):**

- `purse.available` هرگز منفی نمی‌شود.
- مجموع مصرف هرگز از `purse.approved` بیشتر نمی‌شود.
- خدمت فقط از مرکز، پزشک و فیلد درمان مجاز همان پرونده قابل ثبت است.
- با وجود شکایت مالی باز روی یک قلم، آن قلم وارد صف پرداخت نمی‌شود.
- برداشت نقدی از کیف اعتبار هرگز ممکن نیست.

## ۵. اقساط

### تاریخ‌ها

- **تاریخ تکمیل پرونده** = تأیید نهایی مدارک. فقط شاخص عملکرد است.
- **مبنای سررسید = تاریخ واریز به کیف اعتبار** (`funded_at`).
- قسط اول یک ماه شمسی پس از `funded_at` و بقیه ماه‌به‌ماه.

### قاعده روز سررسید

```
dueDay = روز شمسی تاریخ واریز
اگر dueDay > تعداد روزهای ماه مقصد → آخرین روز آن ماه
مثال‌ها:
  ۳۱ فروردین → ۳۱ اردیبهشت (۳۱ روزه) → ۳۰ مهر (۳۰ روزه)
  ۳۰ مهر → ۲۹ اسفند در سال غیرکبیسه، ۳۰ اسفند در سال کبیسه
```

سررسید در روز تعطیل **جابه‌جا نمی‌شود** مگر اینکه پیکربندی `shift_due_to_next_working_day` فعال باشد (پیش‌فرض: خاموش). `TODO(decision)` — تأیید کارفرما. اگر فعال شود، فقط تعطیل هفتگی و تعطیلی سراسری از جدول `holidays` حساب می‌شوند، نه تعطیلی شهری؛ فقط تاریخ جابه‌جا می‌شود و مبلغ هرگز (تسک ۲-۱، ADR-021).

پیکربندی جابه‌جایی سررسید و روزهای مهلت از نسخه‌ای خوانده می‌شوند که پرونده هنگام ایجاد قفل کرده است؛ تقویم تعطیلات همان تقویم زمان شارژ است (ADR-041).

### گردکردن

```
unit = رقم گردکردن (پیکربندی، پیش‌فرض ۱۰٬۰۰۰ ریال = ۱٬۰۰۰ تومان)
base = floor(total / n / unit) * unit      // همیشه رو به پایین
remainder = total - base * n
installment[1] = base + remainder
installment[2..n] = base
```

واحد گرد کردن اقساط از نسخه‌ای خوانده می‌شود که پرونده هنگام ایجاد قفل کرده است، نه از نسخه زمان شارژ. تغییر بعدی واحد روی پرونده‌های موجود اثر ندارد (ADR-039).

**آزمون ثابت:** `sum(installments) === total` برای هر ترکیب مبلغ و تعداد قسط.

**قاعده سخت (۱۴۰۵/۰۷/۰۵، تأیید مالک):** اگر `total < n × unit` باشد، برنامه پیش از ساخت با خطای روشن رد می‌شود؛ برنامه هرگز قسط صفر ندارد.

### تخصیص پرداخت

بدون جریمه دیرکرد و بدون تخفیف تسویه زودهنگام. ترتیب تخصیص: قدیمی‌ترین قسط سررسیدشده، سپس اقساط بعدی. پرداخت اضافه در `suspense.unallocated` می‌ماند تا تعیین تکلیف.

## ۶. انصراف پس از شارژ

1. ابطال مانده مصرف‌نشده `purse.available`.
2. دریافت کارمزد اقساط سررسیدشده.
3. حذف اقساط باقی‌مانده.
4. محاسبه خسارت با درصد پیکربندی (پیش‌فرض ۱۸٪) که **در هر پرونده قابل تغییر است**؛ تغییر آن نیازمند مجوز `credit.penalty.override`، ثبت دلیل و رعایت سقف اختیار نقش است.
5. همه مراحل در یک `JournalEntry` مرکب یا چند سند مرتبط با `case_id` مشترک.

**اجرا (۴-۸ بخش ۷؛ پاسخ‌های مالک ۱۴۰۵/۰۷/۱۳–۱۴):**
- **دونفره و در یک تراکنش:** نوع `cancel_after_funding`.
- **خدمت ثبت‌شده و قطعی‌نشده:** کل عمل را متوقف می‌کند (پ۹).
- **بند ۱:** ابطال کل مانده مصرف‌نشده، با همان ترتیب ADR-034 و ADR-036.
- **بند ۲ (پ۱۱ الف):** کارمزدِ اقساط سررسیدشده می‌ماند.
  - **چه بخشوده می‌شود:** سهم اقساطِ سررسیدنشده‌ای که هیچ پرداختی ندارند.
  - **ثبت‌ها:** سند تازه (سطر «بخشودن کارمزد»)، و نسخه تازه برنامه که همان مبلغ را از آخرین اقساط دست‌نخورده کم می‌کند.
  - **سهم هر قسط (س۱):** کارمزد ÷ تعداد اقساط، گرد به پایین. ته‌مانده با **قسط اول** است.
  - **محدودیت‌ها:** قسط پرداخت‌شده نه بخشوده می‌شود و نه دوباره دریافت. بخشودن هرگز بیش از کارمزد اقساط سررسیدنشده نیست. هیچ قسطی منفی نمی‌شود.
- **بند ۳ (پ۱۲):** اقساط موجود می‌مانند. فقط بخش ابطال‌شده و کارمزد بخشوده از آن‌ها کم می‌شود.
- **بند ۴:**
  - **نرخ:** همانی که قرارداد هنگام ساخت قفل کرده (س۴، جدول `contract_penalty_terms`).
  - **تغییر نرخ در هر پرونده:** پیش از قرارداد، دونفره، بین ۰ تا ۱۸٪ (پ۱۳). بالاتر فقط با ADR تازه.
  - **مبلغ:** نرخ × وام مصوب (A)، گرد به پایین تا ریال.
  - **وصول:** یکجا، با سررسید «روز انصراف + `repayment.cancellation_penalty_due_days`» (مقدار اولیه ۳۰).
  - **یک‌بار:** هرگز دوبار ثبت نمی‌شود.
- **پایان (س۳):** کیف فقط وقتی بسته می‌شود که مانده یا رزرو بازی نماند؛ وگرنه کل عمل رد می‌شود. Case وقتی بسته می‌شود که هیچ کیف باز دیگری نداشته باشد.

## ۷. تطبیق و پایش

- **کار شبانه:** مقایسه مانده محاسباتی با نمای مادی‌شده؛ هر مغایرت هشدار فوری می‌دهد.
- **گزارش روزانه:** مجموع بدهکار برابر مجموع بستانکار در هر شرکت.
- **پیش‌پرداخت (ADR-034):**
  - **برابری:** مانده `downpayment.held` = جمع فیش‌های پیش‌پرداخت تأییدشده، منهای آنچه هنگام شارژ به کیف رفته، منهای برگشت‌خورده‌ها، منهای استردادشده‌ها در انصراف پیش از شارژ (۴-۸).
  - **منفی نبودن:** این مانده هرگز منفی نمی‌شود (مانده عادی بستانکار).
- **استرداد (ADR-036):** مانده `downpayment.refund_payable` و `fee.refund_payable` هرگز منفی نمی‌شود.
  - **برابری (۴-۸، تأیید مالک ۱۴۰۵/۰۷/۱۴):** مانده هر حساب استرداد = استردادهای ثبت‌شده (انصراف پیش از شارژ؛ و برای پیش‌پرداخت، ابطال‌های پس از شارژ منهای برگشتشان) منهای پرداخت‌های بانکی تأییدشده.
  - **پرداخت بانکی:** دونفره؛ شماره پیگیری بانک الزامی و یکتا؛ هرگز بیش از مانده حساب (پرداخت جزئی مجاز).
  - **یک ثبت برای هر فیش:** هر فیش پیش‌پرداخت تأییدشده دقیقاً یک ثبت هم‌مبلغ دارد.
- هیچ گزارشی روی پایگاه عملیاتی اجرا نمی‌شود.

## ۸. آزمون‌های اجباری

1. جمع بدهکار = جمع بستانکار در هر سند.
2. `purse.available` هرگز منفی نمی‌شود، حتی با ۵۰ درخواست برداشت هم‌زمان.
3. تکرار `idempotency_key` سند دوم نمی‌سازد.
4. مجموع اقساط = کل تعهد، برای ۱۰٬۰۰۰ ترکیب تصادفی مبلغ و تعداد قسط.
5. سررسیدها در ماه‌های ۳۱، ۳۰ و ۲۹ روزه درست محاسبه می‌شوند.
6. قطع اتصال در میانه ثبت خدمت، وضعیت قابل بازیابی می‌سازد و برداشت مضاعف نمی‌دهد.
7. شکایت مالی باز، قلم را از صف پرداخت خارج می‌کند.
8. سند معکوس، مانده را دقیقاً به حالت پیش از سند اصلی برمی‌گرداند.
