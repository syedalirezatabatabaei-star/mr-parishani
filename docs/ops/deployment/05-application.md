# ۵. نصب برنامه

[فهرست راهنما](../deployment-guide.md)

## ۵.۱ گرفتن کد از GitLab

1. روی سرور، با حساب سرویس `sepehr`، یک **کلید استقرار فقط‌خواندنی** (deploy key) در GitLab ثبت شود. کلید خصوصی فقط روی سرور، با دسترسی `0600`.
2. ```sh
   sudo -u sepehr git clone <نشانی-SSH-مخزن-GitLab> /opt/sepehr/app
   cd /opt/sepehr/app
   git checkout <برچسب-نسخه-یا-commit>
   ```
3. **فقط برچسب یا commit مشخص**، هرگز «آخرین main». برچسب و commit در دفتر انتشار ثبت شود.
4. **آزمایش‌نشده** روی سرور. نشانی مخزن **پس از تعیین مشخصات سرور** (GitLab خودمیزبان، تسک ۱۰-۰).

## ۵.۳ ساخت

**آزمایش‌نشده روی سرور.** همان چیزی است که CI و `Dockerfile` انجام می‌دهند:

```sh
cd /opt/sepehr/app
pnpm install --frozen-lockfile
pnpm build
```

- `pnpm install` از mirror npm داخلی (Verdaccio؛ `task-10-1-plan.md` §۲). در اینترنت ملی بی mirror نصب نمی‌شود. **پس از تعیین مشخصات سرور.**
- ایمیج‌ها: `pnpm docker:build` هر چهار را می‌سازد (`sepehr-api`، `sepehr-worker`، `sepehr-web`، `sepehr-admin`) و در پایان یک قرارداد نمونه را در ایمیج worker، بی شبکه و با کاربر `node`، به PDF می‌برد. **آزمایش‌شده** ۱۴۰۵/۰۸/۰۲ روی این ماشین. یکی‌یکی: `docker build --build-arg APP=api --target api .`، همان برای `worker`؛ `docker build -f Dockerfile.next --build-arg APP=web .`، همان برای `admin`. در اینترنت ملی، `pnpm` و بسته Chromium باید از mirror داخلی بیایند (ساخت اول این‌جا یک‌بار در دریافت pnpm از npmjs قطع شد).

**کجا اجرا می‌شوند (تصمیم مالک ۱۴۰۵/۰۸/۰۴):**
- **Postgres مستقیم روی سیستم‌عامل** ([فصل ۳](03-database.md#۳۱-نصب-postgres-17)).
- Redis، ذخیره‌ساز S3، ClamAV و چهار ایمیج برنامه در Docker (`/var/lib/docker`)، هر پورت فقط روی `127.0.0.1` (`-p 127.0.0.1:<پورت>:<پورت>`).
- ظرف‌ها Postgres میزبان را با `host.docker.internal` (`--add-host=host.docker.internal:host-gateway`) می‌بینند. پس Postgres روی `127.0.0.1` و نشانی پل Docker گوش می‌دهد، و `pg_hba.conf` فقط بازه پل Docker را با `scram-sha-256` می‌پذیرد.
- گام‌به‌گام: [`docs/ops/staging-install-sheet.md`](../staging-install-sheet.md).

**ترتیب شروع:** Postgres و Redis و S3 و ClamAV، سپس api، سپس وب و پنل، **سپس worker**. **ترتیب توقف:** worker اول (تا کار نیمه‌کاره نماند)، سپس وب و پنل، سپس api.

**سلامت:** `GET /api/v1/health/live` (زنده است) و `GET /api/v1/health/ready` (به پایگاه و Redis وصل است).

نمونه واحدهای systemd در [فصل ۱۰](10-appendix.md#۱۰۲-نمونه-پیکربندی) (**آزمایش‌نشده**).

## ۵.۵ پراکسی معکوس

یک پراکسی (مثلاً nginx) روی ۴۴۳ دو دامنه را جدا می‌کند:

| دامنه | به | نکته |
|---|---|---|
| `<دامنه-بیمار>` | `127.0.0.1:3001` | وب بیمار و پنل مراکز (`/panel`)؛ `/api/v1` را خود وب به api می‌دهد |
| `<دامنه-پنل-داخلی>` | `127.0.0.1:3002` | پنل داخلی. در پراکسی هم فقط از بازه VPN (لایه دوم؛ لایه اول `INTERNAL_PANEL_CIDRS` در خود api) |
| مسیر فایل‌های عمومی | سطل عمومی S3 | فقط اگر `S3_PUBLIC_BASE_URL` روی همین دامنه است. **پس از تعیین مشخصات سرور** (سؤال ۹ فصل ۱۰) |

الزام‌ها:

- `X-Forwarded-For` و `X-Forwarded-Proto` فرستاده شود؛ `TRUST_PROXY=loopback`.
- اندازه بدنه: دست‌کم ۱۱ مگابایت (پیوست تیکت و فایل امضاشده تا ۱۰ مگابایت).
- خود برنامه سرآیندهای امنیتی و CSP را می‌گذارد (`apps/web/proxy.ts`، `apps/admin/proxy.ts`). پراکسی **CSP دیگری اضافه نکند**، تا دو سیاست با هم نجنگند. HSTS را برنامه نمی‌گذارد (جست‌وجو در کد، ۱۴۰۵/۰۸/۰۲)، پس پراکسی آن را بگذارد (`Strict-Transport-Security: max-age=31536000`؛ `includeSubDomains` فقط اگر همه زیردامنه‌های شرکت HTTPS دارند).
- پورت ۸۰ فقط انتقال به ۴۴۳.

نمونه در [فصل ۱۰](10-appendix.md#۱۰۲-نمونه-پیکربندی) (**آزمایش‌نشده**).

## ۵.۶ TLS — **پس از تعیین مشخصات سرور**

- گواهی و کلید خصوصی گواهی: مالک `root`، دسترسی `0600`، بیرون از مخزن.
- فقط TLS 1.2 و 1.3.
- `blackbox_exporter` انقضا را می‌پاید؛ هشدار در ۶۰، ۳۰، ۱۴ و ۷ روز به دو مسئول (تصمیم مالک ۱۴۰۵/۰۸/۰۲).
- تمدید: روش با مالک (سؤال ۳).

## ۵.۷ ذخیره‌ساز اشیا و ClamAV

- **SeaweedFS** (همان ایمیج قفل‌شده `docker-compose.yml`) یا MinIO؛ روی سرور داخلی (`phase-10-readiness.md` §۶.۲).
- **کمبود در پیکربندی:** `docker-compose.yml` مخزن SeaweedFS را **بی هویت** اجرا می‌کند («accepts any key»). این فقط برای توسعه است. در production هویت و کلید S3 واقعی لازم است. **آزمایش‌نشده.**
- نسخه‌بندی سطل خصوصی روشن (حذف تصادفی برگشت‌پذیر).
- **ClamAV:** امضاها از mirror داخلی `freshclam`. ایمیج امضاهای خودش را دارد، ولی کهنه می‌شوند. حدود ۱٫۵ گیگابایت حافظه.

## ۵.۹ کد پیامکی امضای مالی (ADR-052): روشن کردن پس از استقرار

مهاجرت 0106 این کد را **خاموش** می‌سازد (`identity.financial_step_up`، `enabled: false`). تا خاموش است، تأییدهای مالی بی کد کار می‌کنند و `launch-check` بند ۲۹ هشدار می‌دهد. ترتیب روشن کردن:

1. **شماره اول تأییدکنندگان، روی سرور و نه از API.** برای مدیرعامل، مدیر سیستم و تأییدکننده سوم (مالک / مسئول انفورماتیک):

   ```sh
   ACCOUNT_USERNAME=<نام کاربری صاحب شماره> MOBILE=09XXXXXXXXX OPERATOR=<نام کاربری مدیر سیستم>    WITNESS=<نام کاربری شاهد> REASON='شماره اول تأییدکننده' pnpm --filter @sepehr/api identity:first-approver-mobile
   ```

   - **اجراکننده** همیشه مدیر سیستم است. ابزار نقش او را بررسی می‌کند.
   - **شاهد** کارمند دیگری است و هرگز خود صاحب شماره نیست. برای شماره مالک، شاهد **مدیرعامل** است؛ ابزار بدون او اجرا نمی‌شود. برای شماره مدیرعامل و مدیر سیستم، شاهد مالک است.
   - ابزار فقط شماره **اول** را ثبت می‌کند. حسابی که شماره تأییدشده دارد رد می‌شود.
   - ابزار فقط برای دارندگان «تأیید تغییر شماره امضاکنندگان» کار می‌کند.
   - شماره‌ای که کارمند دیگری دارد رد می‌شود.
   - اجراکننده و شاهد با نام کاربری و شناسه حساب در سابقه ثبت می‌شوند. از شماره فقط چهار رقم آخر ثبت می‌شود.
   - تغییر بعدی شماره مالک فقط از صفحه «شماره امضاکنندگان» و با تأیید مدیرعامل و مدیر سیستم است.
2. **تأییدکننده سوم:** نقش «تأییدکننده سوم تغییر شماره امضاکنندگان» (`mobile_change_approver`) را مالک در پنل «نقش‌ها» به حساب خود (مالک / مسئول انفورماتیک) می‌دهد. `launch-check` بند ۳۰ هشدار می‌دهد اگر این حساب نقش مدیرعامل یا مدیر سیستم، یا هر مجوز امضای مالی دیگری، هم داشته باشد. پس از پایلوت این نقش به یک کارمند جدا واگذار می‌شود (فهرست پیش از راه‌اندازی §۵).
3. **شماره بقیه امضاکنندگان:** هر کس یکی از مجوزهای امضای مالی را دارد، شماره‌اش از صفحه «شماره امضاکنندگان» ثبت می‌شود: مدیرعامل یا مدیر سیستم درخواست می‌دهد و دو نفر جز صاحب شماره تأیید می‌کنند. شماره ۲۴ ساعت پس از تأیید دوم اثر می‌کند. صفحه خودخدمت «تأیید موبایل حساب» شماره امضاکننده را نمی‌پذیرد. بند ۲۷ تا وقتی امضاکننده بی شماره هست هشدار می‌دهد.
4. **قالب دوم کاوه‌نگار در production:** `KAVENEGAR_STEP_UP_TEMPLATE` در فایل محیط worker تنظیم شود (بند ۲۶). سپس از پنل کاوه‌نگار **یک پیام آزمایشی موفق** با همین قالب به شماره یکی از امضاکنندگان فرستاده شود.
5. **روشن کردن، دونفره:** پنل «تنظیمات» ← «هویت» ← «کد پیامکی امضای مالی» ← روشن، با دلیل. مدیر سیستم پیشنهاد می‌دهد و «تأییدکننده تنظیمات فنی» (`technical_config_approver`، از 0107) همان صفحه را تأیید می‌کند. دارنده این نقش را مالک روز راه‌اندازی تعیین می‌کند: نه مالک، نه مدیر سیستم (`launch-check` بند ۳۱). از این لحظه هر درخواست و تأیید مالی کد می‌خواهد و بند ۲۹ سبز می‌شود.

پیش از روشن کردن، گزارش `docs/ops/m3-pending-requests.sql` گرفته شود. هر درخواست منتظر با دلیل «استقرار م۳» رد و دوباره ثبت می‌شود.
